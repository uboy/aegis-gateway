# Telegram Proxy (WebProxy & MTProxy): Архитектурное руководство

Руководство по архитектуре и обслуживанию защищенного шлюза Telegram в Aegis Gateway на базе единого порта 443.

## Обзор архитектуры

Все клиентские подключения Telegram маршрутизируются через единый внешний порт **443 TCP**, управляемый HAProxy, что исключает необходимость открытия нестандартных портов (например, 8443) и обеспечивает маскировку под легитимный HTTPS-вебсайт.

| Компонент | Слушающий порт / интерфейс | Назначение |
|---|---|---|
| **HAProxy Ingress** | `0.0.0.0:443`, `[::]:443` | Внешний L4-маршрутизатор, разделяет входящий трафик по SNI и ALPN |
| **Caddy** | `127.0.0.1:4431` | Терминация реального TLS, выдача сайта-заглушки и проксирование WebSocket |
| **tproxy-server** | `127.0.0.1:8080` | WebProxy реле для клиентов Telegram Desktop (HTTP/2 -> MTProto) |
| **mtproxy.service** | `127.0.0.1:2398` | Локальный RPC-транспорт к дата-центрам Telegram (DC1–DC5) |
| **mtproxy-tls.service** | `127.0.0.1:2399` | Fake-TLS бэкенд для мобильных клиентов Telegram (iOS / Android) |

---

## 1. Схема движения трафика

### Telegram Desktop (WebProxy)
1. Клиент подключается по HTTPS к `https://<DOMAIN>:443`.
2. HAProxy направляет трафик с ALPN на локальный Caddy (`127.0.0.1:4431`).
3. Caddy передает сессию в `tproxy-server` (`127.0.0.1:8080`).
4. `tproxy-server` преобразует веб-сокеты в бинарный протокол MTProto и отправляет на внутренний бэкенд `mtproxy` (`127.0.0.1:2398`).
5. Демон `mtproxy` передает данные в дата-центры Telegram.

### Telegram Mobile (Fake-TLS MTProto)
1. Клиент подключается к порту **443** с секретом `ee<secret><hex_domain>`.
2. HAProxy определяет SNI прокси-домена в TLS ClientHello и перенаправляет соединение на `127.0.0.1:2399` (`mtproxy-tls`).
3. `mtproxy-tls` валидирует секрет и маршрутизирует пакеты в Telegram.

### Неавторизованные запросы и сканеры
Любой входящий запрос на порт 443 без валидного секрета или с некорректным SNI попадает в Caddy fallback и получает нейтральную веб-страницу (`index.html`) со строгими HTTP-заголовками, не выдавая присутствия прокси-служб.

## 2. Диагностика и обслуживание

Проверка статуса служб на сервере:
```bash
systemctl status haproxy caddy tproxy-server mtproxy mtproxy-tls
```

Проверка локальных сокетов:
```bash
ss -tulpn | grep -E '443|2398|2399|8080'
```

Просмотр журналов маршрутизации:
```bash
journalctl -u tproxy-server -u mtproxy -u mtproxy-tls --since "30 minutes ago" -n 100
```
